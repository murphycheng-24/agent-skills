# 计划反对者审查

将计划当作尚未通过的提案审查。目标是帮助决策，不是为了凑质疑数量，也不是把简单方案机械地判为更好。

## 输入与边界

1. 读取用户提供的计划、目标、约束和已有证据；不臆造工期、依赖、流量、成本或安全风险。
2. 若任务涉及仓库，先读相关源码、测试和项目规范；再完整阅读内置的 `references/karpathy-guidelines.md`。不得依赖任何外部 Karpathy 文档。
3. 不实施计划；本 Skill 只做审查与方案优化，除非用户明确要求落地。
4. 将每条质疑标为：已证实、合理风险、待确认。待确认项要写出获得答案的最小方式。

## 内置 Karpathy 准则

`references/karpathy-guidelines.md` 是本 Skill 的准则原文。开始审查前必须完整阅读；下方是将其转为反对者提问的速查映射，不替代原文。

## 第一层：Karpathy 行为准则审查

对计划逐项检查；只报告会改变决策的发现。

| 准则映射 | 反对者问题 |
|---|---|
| 读代码、复用既有模式 | 计划是否基于实际代码、测试和既有能力，还是凭空设计？ |
| 假设、取舍、可验证目标 | 关键假设、不可逆选择和验收标准是否明确？ |
| 简单性与手术式改动 | 是否有“以后可能需要”的抽象、重构、配置或依赖？最小改动是什么？ |
| 验证与调试 | 每个关键风险是否有能失败的验证，而不只是“补测试”？ |
| 目标驱动与范围控制 | 每一步是否直接服务目标？哪些是 Kitchen Sink、Wrong Abstraction 或 Runaway Refactor？ |
| 依赖与沟通 | 新依赖是否必要、可维护且有替代？不确定性是否被明确暴露？ |

## 第二层：通用质疑

按以下维度扫描。每个维度最多保留一条最有决策价值的质疑；无事实依据时写“待确认”，不要编造。

| 角度 | 质疑重点 |
|---|---|
| 完整性 | 主流程外的异常、边界、退化和失败路径是否遗漏？ |
| 优先级 | MVP 必须做的三项是什么？哪些可砍而不影响目标？ |
| 工期 | 估算是否有拆分和依据？联调、验收、迁移是否被漏算？ |
| 依赖 | 有哪些人、系统、审批或第三方阻塞？哪些可并行？ |
| 成本 | 实施、迁移、运行、回归和机会成本由谁承担？ |
| 目标偏差 | 每项工作如何直接影响原始目标？有没有为了技术而技术？ |

## 第三层：专业审查

仅对计划实际涉及的项审查；不相关时明确 `不适用`。检查架构合理性、数据流和兼容、权限安全、可观测性、回滚、测试覆盖、性能八项。

- 对数据或存量格式变更，必须问：旧数据、消费者、迁移、双写或回滚怎么处理？
- 对上线变更，必须问：失败如何发现、如何止损、如何回退？
- 对性能结论，必须要求目标负载、延迟或容量依据。
- 对测试结论，必须指出关键行为和失败场景，而不是泛称“单元测试/集成测试”。

## 优化方案规则

1. 先写原计划的 3 个优点，避免把反对意见伪装成客观事实。
2. 再写更简单方案的 3 个优点，且必须说明它放弃了什么能力。
3. 提出一个 `最小可行替代方案`：最多 5 步，只保留直接达成目标、可验证、可回滚的工作。
4. 列出原方案的 3 个最强弱点，按影响排序。每个弱点都要对应替代方案中的一个动作或明确的延期理由。
5. 给出真实推荐：原方案、替代方案，或“先替代后扩展”；不得为了中立而模糊折中。

## 固定输出格式

使用以下结构，简洁作答：

```markdown
## 审查结论

一句话推荐：……

| 维度 | 判断 | 证据 / 待确认 |
|---|---|---|

## 原方案的 3 个优点

1. …

## 更简单方案的 3 个优点

1. …（代价：…）

## 反对者的 3 个核心质疑

1. **[影响级别] 标题**：质疑。优化动作：…

## 最小可行替代方案

1. …（验收：…）

## 真实推荐与触发条件

推荐：…

升级到完整方案的触发条件：…
待确认：…
```

缺少关键事实时，不阻塞基础结论；将建议限定为条件性结论，并把待确认项放在最后。
