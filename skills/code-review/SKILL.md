# 代码审查 Skill

## 目标

给定 git 提交区间（起始 commit → 结束 commit），自动完成：

1. **变更梳理** —— 列出所有涉及文件及其改动摘要
2. **影响范围与隐藏范围分析** —— 识别模块依赖、核心链路和未直接修改的潜在受影响方
3. **行为迁移分析** —— 对比关键链路改动前后的触发条件、结果和兼容性
4. **Bug 风险报告** —— 按 P0/P1/P2 分级标注隐患
5. **测试建议范围** —— 为迁移行为、隐藏范围和风险点给出可执行覆盖建议

---

## 工作流程

### Phase 1：采集提交信息

1. 获取提交列表（含作者、时间、提交信息）：
   ```bash
   git log <start>^..<end> --oneline --reverse
   ```
2. 获取每次提交的文件变更统计：
   ```bash
   git diff --stat <start>^ <end>
   ```
3. 获取完整 diff 内容（用于代码级分析）：
   ```bash
   git diff <start>^ <end>
   ```
   > 如果 diff 过大，按文件逐一读取关键文件内容

### Phase 2：代码理解与影响范围分析

- 阅读每一个被修改文件的 **当前版本**
- 识别被改动函数/方法/组件的所有调用方
- 识别隐藏范围：未直接修改但受共享状态、API contract、事件、路由、持久化或间接调用链影响的入口和消费者；每项都记录搜索/调用链证据。未发现时明确写“未发现隐藏范围”。
- 为每个业务行为填写行为迁移矩阵：改动前、触发条件、改动后、受影响消费者、兼容性风险和证据；禁止只用 diff 推断而不追踪调用方。
- 判断改动是否触及以下高风险区域：
  - 状态管理（store / vuex / pinia / redux）
  - 数据持久化（save / restore / serialize）
  - 事件监听器生命周期（add/remove EventListener）
  - 异步流程（Promise 链、async/await 竞态）
  - WebGL/Canvas 资源管理（context、texture、framebuffer）
  - 路由生命周期（beforeRouteLeave、onBeforeUnmount）

### Phase 3：Bug 风险分级

按以下标准打分，写入分析报告：

| 级别  | 含义                                         | 行动要求               |
| ----- | -------------------------------------------- | ---------------------- |
| 🔴 P0 | 可能导致功能崩溃/数据丢失/资源泄漏的严重问题 | **必须修复，立即修复** |
| 🟠 P1 | 影响用户体验、数据一致性或潜在性能退化       | 建议尽快修复           |
| 🟡 P2 | 代码质量问题、潜在边界 case、技术债务        | 迭代时修复             |

对每个风险点，提供：

- 问题描述
- 涉及文件/行号
- 复现路径（如何触发）
- 推荐修复代码片段

### Phase 4：生成分析报告

使用 `references/report_template.md` 作为报告模板，填充以下章节：

- 提交区间概览（N 次提交，涉及 X 个文件）
- 核心变更摘要（按模块分组）
- 影响范围矩阵
- 隐藏范围
- 行为迁移矩阵
- P0/P1/P2 风险清单
- 推荐修复代码
- 测试建议范围
- 提测清单（影响范围、必测场景、建议测试方式、风险点）

**报告合同：** “隐藏范围”“行为迁移矩阵”“测试建议范围”是每次审查都必须出现的二级标题。无发现、无迁移或不适用时，保留对应章节和表格，写明结论及搜索/审查依据；不得删除或以其他章节替代。

直接在任务响应中输出报告；仅在用户要求文件时写入 artifact。

### Phase 5：自动化测试（可选，询问用户）

完成报告后，主动询问：

> "是否需要我为报告中标注的核心逻辑生成自动化测试脚本？（Vitest / Jest / Playwright，根据项目技术栈自动选择）"

如果用户同意，执行以下步骤：

1. **检测测试框架**：读取 `package.json` 中的 `devDependencies`，识别 vitest/jest/playwright
2. **确定测试目标**：优先覆盖 P0/P1 风险点涉及的函数/组件
3. **生成测试文件**：
   - 命名规则：`<原文件名>.spec.ts`（或 `.test.ts`）
   - 放置位置：与被测文件同目录，或项目约定的 `__tests__` 目录
   - 覆盖场景：正常路径 + 边界条件 + 已发现的 Bug 复现用例
4. **写入文件**并告知用户如何运行

## 注意事项

- 如果用户只提供了一个 commit hash，询问确认是否要分析「该提交与前一提交的差异」
- 如果提交区间超过 50 次提交，先按模块汇总，再展开高风险文件的详细分析
- Windows 环境使用 PowerShell，不使用 `head`/`grep` 等 Unix 命令，改用 PowerShell 等效命令
- 遇到 git 中文路径乱码时，先执行：`git config --global core.quotepath false`
- 分析 Vue 组件时，重点关注：`onMounted`/`onUnmounted` 是否对称清理、`watch` 是否有 `immediate` 副作用、`emits` 是否全部声明
